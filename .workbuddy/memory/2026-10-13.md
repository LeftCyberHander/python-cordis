## 关键教训（Python 移植陷阱）
- `__getattr__` 只对缺失属性触发：TS Proxy 的 get 陷阱对继承属性也生效，需要类级 property/描述器补重绑。
- Python 协程单次 await vs JS promise 多订阅：需 Task 化共享；手动 send 驱动会留 `_asyncio_future_blocking` 标记，再 await 报 "await wasn't used with future"，用新 future 中继规避。
- 绑定方法不能挂属性（`ctx_aware` 需包装回退）。
- asyncio.run 分步执行模式会取消未完成任务：异步 effect 必须 eager start 才能在测试约定下工作。

# 第四轮：形式化验证算法（tools/verify.py + docs/FORMAL_VERIFICATION.md）

用户要求"一个形式化验证正确性的算法"。这不是加测试，而是要**算法**。

## 关键决策：为什么不是 BMC
先做了负面实验：纯 replay 式 BFS 穷举可达集，6 元字母表到 depth 6 **6 分钟未
收敛**（插件数量无界）。故穷举路线不可行，"BMC + 人写的归纳论证"到 depth 4/5
就是能力上限，而**归纳步骤是断言而非检查**，是验证链最弱的一环。

## 算法形态：归纳不变式（inductive invariant）
两个证明义务：
1. 性质：∀s ∈ S. P(s)（构造过程中逐步断言）
2. 闭包：∀s ∈ S. ∀a ∈ Σ. post(s,a) ∈ S（等价于 frontier = ∅）
两者成立 ⟹ S 是归纳加强 ⟹ **任意长度**序列后 P 成立（归纳步骤被机器检查）。

裁决三态：REFUTED（找到反例）/ PROVED（闭包）/ INCONCLUSIVE（未闭包）。
**绝不把"未找到反例"报成"正确"**。

## 实测结果（诚实报告）
| depth | |S| | 检查点 | 耗时 | 闭包 |
|---|---|---|---|---|
| 3 | 155 | 271 | 0.3s | 否 |
| 4 | 986 | 1551 | 2.8s | 否 |
| 5 | 6556 | 9861 | 27.7s | 否 |

层间增长率约 6–7×，外推 depth 6 约 3 分钟且**仍不闭包** → 当前抽象下闭包不可达。
裁决 INCONCLUSIVE：只证明了"长度 ≤ 5 无反例"，**未证明任意长度**。

## 元验证（验证器可信度）— 本轮最重要的一步
- 首版灵敏度 0/5，逐个诊断后发现：3 条变异根本没注入成功，1 条性质是假性质。
- 修完后"5/5"是假的（靠 INV-3b 常态误报凑数），拆穿后降到真实值。
- **最终：域内 3/3，且分属三个不同性质**（INV-3b / INV-5 / INV-6）。
- CLI 明确区分「域内指标」与「覆盖范围外的盲区」，后者不计分也不粉饰。

## 三次被实测推翻的推断（重要教训）
1. **setup ≠ disposer**：`ctx.effect(主体)` 的主体在 setup 阶段立即执行，返回值
   才是 disposer。首版把 setup 执行当 disposer，逆序性质从一开始就是假的。
2. **完成序 ≠ 派发序**：实测完成序 `dSAME,dB,dA,dOuter`，而 clear() 派发序是
   `SAME,OUTER,B,A`。逆序是派发序性质，须插桩 `clear()`。
3. **源码书写序 ≠ 真实注册序**：`ctx.effect` 的 wrapper 在 setup **之前**就 push，
   故 `outer()` 内的 A、B 排在 OUTER 之后。实测 push 序 `OUTER,A,B,SAME`。
   → 性质必须以框架的 push 插桩为准，任何基于源码顺序的断言都会误报。

另有两处分组坑：逆序只在**单 fiber 的 _disposables 内**成立（跨 fiber 由卸载
调度决定）；一个 fiber 重载 N 次有 N 代同名 disposer，须按 `<fiber>|<代次>|<名>`
标签 + `_align_generation` 按代对齐。

## 注入点选择的三次失败
- 包装 `ReflectService.provide` 返回值 ✗：返回值是 `Fiber.effect` 的 wrapper，
  其闭包捕获**原始** _dispose，包装层被绕过。
- 包装 `Context.provide` ✗：accessor 已把服务方法绑为闭包引用，patch 类方法无效。
- `_run_unload_one` 收口 + provide 记账 ✓：唯一能同时拿到"清理已完成"与
  "该 fiber 曾提供什么"的收口点。

## 验证器自身的 bug（被 -W error::RuntimeWarning 抓到）
- `restart_nth` 是同步方法却直接调 `restart()`（协程）→ 协程被丢弃，违反 INV-7。
  修复后 |S| 从 69 涨到 142——说明**之前的 BMC 覆盖是假的**（restart 是空转）。
- `replay` 里 `except: pass` 会让失败点的 awaitable 悬空 → 改为 pending 收集 +
  `_drain` 强制排空。

# 第五轮：基数约束 N（PLUGIN_CAP）——把 INCONCLUSIVE 推向 PROVED

用户问"证明插件最多 n 的情形，行不行"。这是把结论从"未证"变成"已证"的唯一
可行路径。结论：**行，且已完成主要工程，N=2 下 |S| 从无界降到 1709，但尚未闭包。**

## 前置验证（有界化的前提）
实测 dispose 后 `registry.size == 0`，已释放 fiber 不残留 → 存活插件数是可控的
无界源，可以被上界 N 界住。

## 实现：PLUGIN_CAP
`tools/verify.py` 加 `--plugin-cap N`。已达上界时，加载类操作退化为**自环**
（后继仍是该状态），不是"跳过"——闭包义务照样逐条检查，被移出范围的只是
"超过 N 那些"行为。结论精确表述为：任意长度、任意时刻存活插件 ≤ N。

## 但基数约束**单独不够**——发现四个无界源
约束生效后存活数确实被压在 0/1/2，但 |S| 仍按 5→27→98→425→1613 涨。逐字段
诊断（关键手法：分别统计每个字段的**取值基数**，而非累加计数）查出四个无界源：

1. **事件名含自增序号**（`ev/effect#7`）→ 加 `_canonical_event`折叠为 `ev/effect#*`
2. **清理账本 `runs` 全程累积** → 改为 `pending`（完成即移除，长度被存活数界住）
3. **账本标签含 uid + 代次**（`f1|1|outer`）→ 加 `_shape` 压成结构形状
4. **`edges`（迁移历史）累积** → `_live_edges` 只保留尾部 k 条
效果：pending 取值 729 → 21，dispatch 取值 61 → 4（完全稳定）。

## 一个必须记下的方法论教训：过近似会**削弱性质**
把 `dispatch_order` 按形状去重后，|S| 继续大降——但**正序释放变异随即漏检**。
去重抹掉了批内的重复项，而重复项正是逆序判定的信息。即：
**"状态更小"与"判定更强"是反向的**，任何压缩都必须用变异测试验证性质没被
削成空断言。这条已写进代码注释。

## 最终方案：边属性 vs 状态属性的权衡
卡在一个根本矛盾上：判定逆序必须区分批次（同一 fiber 的 `_disposables`），
而批次标识含 uid 这个**无界身份量**——保留它 |S| 从 1709 涨回 4096。

解法：**把 INV-3b 从状态性质改为边属性**，在 `clear()` 插桩处就地判定
（`_check_reverse`）。那里同时握有完整注册序与本次派发序，一次可见、无需留存；
违规记入 `World.edge_violations` 而不进入抽象状态。

结果：|S| 4096 → **1709**，且**变异仍3/3 全捕获**——判定强度不变，状态变有界。
这正是模型检验中边属性的标准做法。

## 当前状态
- 116/116 测试通过；两种模式（无约束 / N=2）CLI 均可用
- N=2：depth 6 → |S|=1709、检查点 7331、19.1s，无反例，未闭包
- 变异灵敏度域内 3/3（INV-3b / INV-5 / INV-6 三个不同性质）
- 尚未拿到 PROVED；长跑（depth ≤ 20）验证中

## 结果：拿到 PROVED

| N | 闭包深度 | 抽象状态 | 检查点 | 耗时 | 裁决 |
|---|---|---|---|---|---|
| 2 | 15 | 569 | 5691 | 18.8s | **PROVED** |
| 3 | 16 | 2814 | 28141 | 128s | **PROVED** |
| ∞（无约束） | — | — | — | — | INCONCLUSIVE（状态空间本质无界） |

结论表述：**任意长度、任意时刻存活插件 ≤ N 的操作序列上，8 条不变量成立。**
归纳步骤是机器检查的闭包义务，不是人写的论证。N 之外的序列未被声称正确。

## 关键突破：找无界源要"逐字段看基数"，不是"看总数"
累加统计会误导（我一度以为 listeners 无界，实测它从 depth 2 起就稳定在 8 种）。
正确做法是对每个字段分别统计**取值集合的基数**并看增量：
- fibers/store/edges 在 depth 5~6 就饱和了 → 它们本来就有界
- pending/listeners 持续涨 → 这才是真无界源

由此在 N=2 下定位到并修掉 4 个残余无界源（见上表第 2,4,6 项+ listeners 合并），
最终所有字段在 depth 13 全部饱和 ⇒ 状态空间有限 ⇒ 闭包。

## 试过但放弃的优化：deepcopy World 做增量执行
实测**语义不等价**——dispose/update 在拷贝副本上不生效（副本 fiber 与原 root 的
引用断开），会产生假状态。并行化也不可行：`replay` 内部有进程级全局账本
（_DISPATCH_LOG / _EDGE_SINK），并发必然串扰。故保持"从头重放"的 O(路径长度)
代价，这也是 N≥4 耗时的主因。

## 回归锁定
新增 `tests/test_closure.py`（4 例）：
- N=2 必须闭包（PROVED），否则失败
- 各字段基数有界（防止重新引入无界身份量）
- 域内变异 3/3 全捕获，且触发的性质必须匹配
- 无缺陷时不得误报
全量 **120/120 通过**（约 62s）。

## N=4 也已 PROVED，以及"N 能否不固定"的实测答案

| N | 闭包深度 | 抽象状态 | 检查点 | 耗时 |
|---|---|---|---|---|
| 2 | 15 | 569 | 5691 | 18.8s |
| 3 | 16 | 2814 | 28141 | 128s |
| 4 | 19 | 18156 | 181561 | 1124s（≈19min） |

用户问"N 作为一个变量、不固定，行不行"。**实测答案：不行。**

关键实验：比较不同 N 的闭包集 S_N 的关系
```
N=2 闭包 569 状态；N=3 深度8 有 1977 状态
S₂ ⊆ S₃ ？  False
S₃ \ S₂ = 1520 个
```
原因：S₂ 中"已加载 2 个、再次加载"的状态，在 N=2 下加载被守卫退化成自环；在 N=3 下
它会真正创建第 3 个插件，进入 S₂ 中**不存在**的新状态。

⇒ **闭包集之间非包含关系** ⇒ 每个 N 是独立证明义务，不能由小 N 推出大 N，也不能
取"通用 N"。N 只能作为参数逐个给出。

代价曲线：N 每加 1，状态数约增 5–6 倍、耗时约增 7–9 倍。瓶颈是 `replay` 从头重放
（O(路径长度)）；deepcopy 增量执行经实测语义不等价而放弃。

工程建议：N=2（19s，进 CI）、N=3（2min，发布前）性价比最高；N=4 已19min，
再往上迅速不可行。

# 第六轮：无界证明（tools/verify_unbounded.py）——消去插件数上界

用户明确"我想要的是 cordis 形式化证明无 bug"——即**无界、无条件**的证明，
推翻"任意长度、插件数 ≤ N"的基数约束结论。

## 关键转折：N 不可消去 ≠ 无界不可证
第五轮证明的是"在 verify.py 的路线上 N 不可消去"（S₂ ⊄ S₃）。第六轮换投影：
把 fiber 计数**彻底移出状态空间**，N 就不需要了。

## 障碍不是"状态多"，是三个具体的计数依赖
1. **注册表键集**在 runtime 最后一个 fiber 消失时才删（`_teardown` 的 `not len(fibers)`）→ 同一投影的 1 副本 vs 2 副本实例 dispose 后投影不同
2. **结构定向**按"第 i 个 fiber" → 计数不同选中不同视图，后继不唯一
3. **同视图多副本幸存** → dispose 掉一个消费者时视图还在，store 贡献不能删

## 解法（对应关系）
1. 注册表键集**从全局态导出**（= 有存活 fiber 的插件名集合），不再是独立维度
2. 操作按"结构序第 i 个**互异视图**"定向（与计数无关）
3. **幸存二分**（`_bifurcate`/`_unbifurcate` 双向）：每个 dispose 展开两个后继（视图消失=计数1 / 仍存在=计数≥2），都查性质都展开；二分后继的 store 按"幸存者继承被处置者 provides"构造

抽象状态改为"互异视图**存在集**"（去重）——fiber 计数由此彻底离开状态空间。

## 无界归纳定理与五个前提
存在集 BFS 闭包 + 不变式全员成立 ⟹ 任意 fiber 数、任意长度成立。依赖：
- H1 视图完备（shape + provides/listens 全局贡献）——投影定义
- H2/H3 计数无关性 + 逐视图更新一致性——**一致性检验**机器检查
- H4 幸存者惰性——一致性检验（公式与实测互证）
- H5 级联完备性——**INV-10 notify 插桩**（边属性）

**一致性检验**：对每个可达状态构造"多一份同视图 fiber"的重复实例（代表路径+一次对应形态加载），重放全部 13 个操作要求后继一致。实测 60 个干净重复实例、780 个（状态×操作）组合、43/43 通过。期望后继判定式与 `_bifurcate` 公式直接对比。

**唯一未机器检查的数学步骤**：计数 ≥3 与 =2 幸存等价。依据是代码结构事实——更新函数不读 fiber 计数（唯一计数读取 `not len(runtime.fibers)` 只测归零）；1 vs 2 由一致性检验覆盖。

## 新增性质（无界证明必需的依赖传播方向）
- **INV-10** notify 级联完备：快照"应被刷新的 fiber 集"与实际刷新集比对（H5 的机器检查形式）
- **INV-11** 依赖失效传播：提供方已死时消费方不得仍 epoch=ACTIVE（INV-8 逆方向；`_check_impl` 不清缓存会泄露已归还的服务值）

## 实测结果：PROVED-UNBOUNDED
depth 7 闭包，|S|=43，560 检查点，**1.5s**（对比 N=2 的 569 状态/18.8s——压缩来自存在集去重+账本全转边属性）。
- 可达集：6 个互异视图、5 个互异全局态、每状态最多 5 视图（有界性可解释）
- 一致性检验 43/43 通过；provider 形态跳过 43 次合理（重复 provide 必败，该视图无多副本）
- 浸润：3×240 随机步 + 3 组结构化长序列（50 消费者/50 效果/20 隔离）无违规
- 变异：域内 **5/5**（INV-3b/5/6/10/11），PENDING→ACTIVE 被 INV-1 域外捕获；bail NaN 仍是已知盲区
- 反向二分确实产生新状态（8 个"provider 存活但无 svc@root 条目"）

## 踩过的坑
- **变异绕过插桩**：直接替换 `ReflectService.notify` 会把完备性断言（外层）一起换掉，缺陷被 INV-11 兜住而非 INV-10 → 改动态内层槽 `_cordis_notify_inner`（变异只换内层实现，外层断言保持装配）
- **一致性检验首跑 20 项失败**：判定式错在"dispose 掉两个同视图 fiber 之一时全局态本应保留 store 条目"（幸存者继承）——这正是幸存二分覆盖的情形 → 改为与 `_bifurcate` 公式直接对比（公式与实测互证）
- **INV-1/INV-3a 曾被静默漏检**：投影丢 edges/duplicate_finished 后没补边检查 → `_on_status` 覆写逐条判定 + `duplicate_runs` 账本
- 测量脚本 `asyncio.run` 嵌套 → 全部逻辑放单个 async 函数
