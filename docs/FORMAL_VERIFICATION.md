# cordis_py 正确性的形式化验证：算法、证明义务与实测结论

本文给出 `tools/verify.py`（基数约束）与 `tools/verify_unbounded.py`（无界）
所实现的**形式化验证算法**：它们的形式化定义、判定过程、结论的强度边界，以及
"验证器本身是否可信"的元验证结果。

阅读顺序建议：§1 结论 → §2 算法 → §3 证明义务 → §4 元验证 → §5 残余风险。

## 2. 问题的形式化

### 2.1 转移系统

给定初态 `init`、操作字母表 `Σ`、确定性后继函数 `δ`，框架的执行语义是一个
转移系统 `(S, Σ, δ, init)`。

**关键困难：`|S|` 无界。** 插件可以无限加载，因此可达集随序列长度增长。实测：
朴素 BFS 穷举在 6 元字母表上到深度 6 仍未闭包（6 分钟未收敛，见 §5.1）。这
直接排除了"穷尽可达集"的思路。

### 2.2 抽象与性质

**抽象投影** `α: S → A`：把具体状态压成可哈希的抽象状态
（`AbstractState`）。投影必须满足**性质是 α 的函数**，否则性质无法在抽象层
判定。`project()` 把 INV 所需的全部可观测量都纳入投影——包括监听器归属、清理
账本（登记/完成/派发/注册四本账）、store 中提供方的存活标记。

**性质** `P: A → {True, False}`：`verify.py` 有 8 条不变量（`_p_inv1` …
`_p_inv8`），`verify_unbounded.py` 有 8 条（INV-2/4/5/6/8/11 + 两条由边属性
承担的迁移与 disposer 性质），每条是抽象状态的纯函数。全部清单见 §4.1。

## 3. 算法

### 3.1 伪码

```
Verify(Σ, P, max_depth):
    S ← { α(init) }                          # 可达集
    检查 P 在 α(init) 上                       # 义务 1（初态）
    if 违反: return REFUTED(反例 = 空路径)

    frontier ← { 空路径 }
    for depth = 1 .. max_depth:
        for each 路径 p in frontier, each a in Σ:
            s ← α(replay(p · a))              # 重放并投影
            if s ∉ S:
                S ← S ∪ {s}
                检查 P 在 s 上                 # 义务 1（可达态）
                if 违反: return REFUTED(反例 = p · a)
                frontier ← frontier ∪ {p · a}
        if frontier = ∅:
            return PROVED(S 是归纳不变式)      # 义务 2（闭包）成立
    return INCONCLUSIVE(S 未闭包)
```

### 3.2 为什么这构成"任意长度"的证明

`PROVED` 需要两个义务同时成立：

- **义务 1（性质）**：`∀ s ∈ S. P(s)` —— 由构造过程逐步断言；
- **义务 2（闭包）**：`∀ s ∈ S. ∀ a ∈ Σ. δ(s, a) ∈ S` —— 等价于 `frontier = ∅`。

两者一起给出 `S` 是关于 `P` 的**归纳加强**。于是对任意长度的操作序列
`σ = a₁…a_N`（**N 无界**）：

```
α(init) ∈ S                        (初态在 S 中)
若 α(δ(前缀_k, σ)) ∈ S，则 α(δ(前缀_{k+1}, σ)) ∈ S   (闭包性)
⟹ α(δ(init, σ)) ∈ S
⟹ P(δ(init, σ))                    (义务 1)
```

这与 `docs/CORRECTNESS.md` §3 里"人写的归纳论证"的区别是：**归纳步骤被机器
检查了，而不是被断言的**。BMC 的结论只能覆盖锚定长度；本算法一旦返回 `PROVED`，
覆盖长度无界。

### 3.3 一个必要的设计约束：操作必须由抽象状态定向

去重的正确性要求"同一抽象状态 → 同一操作 → 同一抽象后继"。若操作按 `uid`
序号选择 fiber（`tests/test_properties.py` 的原做法），则同一抽象状态的不同
具体实例会选中不同 fiber，后继不唯一，去重就会丢掉真实行为。

因此 `World._ordered_fibers()` 按**结构特征**（状态、disposable 数、inject 键、
hook 键）排序，而不使用 `uid`。这是算法成立的前提，不是优化。

### 4.3 INV-3b 的推导过程（两处反直觉的实测结论）

这个性质不是照着"应该是逆序"写出来的，是被实测**纠正**了三次：

1. **setup 与 disposer 是两件事。** `ctx.effect(主体, label)` 的**主体在 setup
   阶段立即执行**，其返回值才是 disposer。第一版把 setup 执行当成 disposer
   执行，于是"逆序"从一开始就是假性质。
2. **完成序 ≠ 派发序。** 包装后的 disposer 经协程调度，实测完成序为
   `dSAME, dB, dA, dOuter`，而 `clear()` 的派发序是 `SAME, OUTER, B, A`。
   逆序是派发序的性质，完成序会被调度打乱，故改为插桩 `clear()` 记录派发序。
3. **源码书写序 ≠ 真实注册序。** `ctx.effect` 的 wrapper 在 setup 执行**之前**
   就被 push，故 `outer()` 内注册的 A、B 排在 `OUTER` 之后。实测 push 序
   `OUTER, A, B, SAME`，其逆序恰好等于 `clear()` 的 yield 序。任何基于源码
   书写顺序的断言都会误报，故性质直接以框架的 `push` 插桩为准。

此外，逆序只在**单个 fiber 的 `_disposables` 内**成立（跨 fiber 的释放顺序由
卸载调度决定），且一个 fiber 重载 N 次就有 N 代同名 disposer——故标签格式为
`<fiber键>|<代次>|<局部名>`，并按 fiber 分组、按代次对齐后才比较
（`_align_generation`）。这两处若不处理，正常路径会持续误报。

## 5. 元验证：验证器本身可信吗

一个"永远通过"的验证器毫无价值。本节用**变异测试**给出验证器灵敏度的经验
证据：把真实历史缺陷重新注入框架，要求算法报出反例。

重蹈：`accessor` 返回值替换无效（框架从不调用它，卸载走 effect 内部 disposer）；
`resolve_config` 包装器先调原函数（异常抢先抛出，缺陷走不到）；清空根 fiber 放在
`Fiber.__init__`（内置注册发生在它**返回之后**，清的是空列表）；把 `_HookMap`
的 store 换成裸 dict（它的保护来自方法路由而非 store 类型）。

其中"notify 级联遗漏依赖方"的注入点换过一次：第一版直接替换
`ReflectService.notify`，把级联完备性断言（外层）一起换掉，缺陷被 INV-11
兜住而非 INV-10——即变异**绕过了它本该 exercised 的性质**。改为动态内层槽
（`_cordis_notify_inner`，变异只替换内层实现、外层断言保持装配）后才正确
触发 INV-10。这与 §5.3 记录的三次失败是同一类教训：**注入点必须让变异精确
落在目标性质上**。

### 5.2 域外变异为何不计分

`bail` 判据放行 NaN **不被 INV-1~8 观测到**：8 条不变量都不检查事件的 bail
判定。把"抓不到"计为漏检会**低估**验证器之外的东西，计为"捕获"则是虚假宣传。
故 CLI 明确区分：域内指标用于判断验证器强度，域外条目用于**量化性质集的
盲区**。这是"未捕获"与"无缺陷"必须分开陈述的典型例子。

关于"PENDING 被误判为 ACTIVE"这条：最初判断它属于域外（理由是 `Fiber.state`
是普通属性、`_get_state` 只在 `_update_state` 内被调用），但 depth=4 的实测
推翻了该判断——它**会**被 INV-1 捕获。原因是 `_update_state` 在某些路径上
会以 `_get_state()` 的返回值直接改写状态，误判后的 PENDING→ACTIVE 会形成
一条不存在的迁移路径。这是**实测修正了推断**的又一例，故保留在表中并标注
"域外（实际被捕获）"，以记录判断与实测的分歧。

## 6. 残余风险（显式陈述，不隐藏）

### 6.1 结论的边界：N 是显式参数，不可消去

已证明的是：**任意长度、任意时刻存活插件 ≤ N** 的操作序列上，8 条不变量成立。
N 之外的序列（同时存活超过 N 个插件）**未被声称正确**——它们被基数守卫移出
了转移系统，不是被证明为正确。

#### 为什么 N 不能"不固定"（实测结论）

一个自然的想法是：把 N 当成证明过程中自由取值的参数，宣称"对所有 N 成立"。
**这条路被实测否定了。** 检查不同 N 的闭包集 `S_N` 之间的关系：

```
N=2 闭包：569 个状态
N=3（深度 8）：1977 个状态
S₂ ⊆ S₃ ？   False
S₃ \ S₂= 1520 个
```

**闭包集之间不是包含关系。** 原因很直接：`S₂` 中"已加载 2 个插件、再次执行
加载"的状态，在 N=2 下该加载被守卫退化成自环；而在 N=3 下它会真正创建第3 个
插件，进入一个 `S₂` 中**不存在**的新状态。

推论：每个 N 对应**各自独立**的证明义务，既不能由小 N 推出大 N，也不能取"通用
的 N"。N 只能作为参数逐个给出。

#### N 的代价曲线

| N | 闭包深度 | 抽象状态 | 检查点 | 耗时 |
| --- | --- | --- | --- | --- |
| 2 | 15 | 569 | 5 691 | 18.8 s |
| 3 | 16 | 2 814 | 28 141 | 128 s |
| 4 | 19 | 18 156 | 181 561 | 1 124 s（≈19 min） |

N 每加 1，状态数约增 5–6 倍、耗时约增 7–9 倍。主要开销来自 `replay` 从头
重放整条路径（O(路径长度)）；该实现上的优化尝试（deepcopy 增量执行）经实测
**语义不等价**而放弃（副本的 fiber 与原root 的引用断开，dispose/update 不生效）。

**工程判断**：N=2（19 s，适合放进 CI）与 N=3（2 min，适合发布前跑）性价比最高。
N=4 已达19 分钟，且随 N 增长迅速逼近不可行的量级。

#### 六个无界源与各自的处理

达到闭包的关键不在基数约束本身，而在把六个无界成分逐一移出抽象状态：

| # | 无界源 | 处理 | 实测效果 |
| --- | --- | --- | --- |
| 1 | 存活插件数 | `--plugin-cap N` 基数守卫（加载操作退化为自环） | 存活数被压在 0..N |
| 2 | 事件名 `ev/effect#7` 的自增序号 | `_canonical_event` 折叠为 `ev/effect#*` | listeners 有界 |
| 3 | 清理账本全程累积 | 改为 `pending`（完成即移除），长度被存活数界住 | runs 长度 0,1,…,6 → 有界 |
| 4 | 账本标签含 uid + 代次 | `_shape` 压成局部名（`A`/`B`/`outer`/…） | pending 基数 703 → 5 |
| 5 | 迁移历史 `edges` 累积 | `_live_edges` 只保留尾部 k 条 | edges 收敛到 35 |
| 6 | `epoch` 含依赖提供方 uid | `_canonical_epoch` 折叠为 `""`/`"ACTIVE"`/`INACTIVE` | fibers 收敛到 15 |

另有一处合并：`listeners` 按规范名合并（折叠后多个事件名映射到同一规范名，
不去重会使 tuple 长度随插件数线性增长）。

#### 一条必须记下的方法论教训

把 `dispatch` 按形状去重后 |S| 大幅下降——但**正序释放变异随即漏检**：去重抹掉了
批内重复项，而那正是逆序判定的信息。即：

> **"状态更小"与"判定更强"是反向的。** 任何抽象压缩都必须用变异测试验证
> 相应性质没被削成空断言。

由此最终采用**边属性**方案：逆序判定移到 `clear()` 插桩处就地完成
（`_check_reverse`），违规记入 `World.edge_violations` 而不进入抽象状态。
判定强度不变（变异仍 3/3 捕获），状态空间从 4096 降到 1709。

### 6.2 无界证明（第六轮）：插件数上界的消去

`verify.py` 的结论带一个显式参数 N。"N 能否不固定"的答案在**那条技术路线上**
是不能（§6.1：`S₂ ⊄ S₃`，每个 N 是独立义务，且代价随 N 爆炸）。第六轮换了
投影，把 N 消去：`tools/verify_unbounded.py` 给出

> **定理（无界归纳）**：若在**存在集**层面的可达集 S 闭包，且不变式在 S 上全员
> 成立，则不变式在**任意 fiber 数、任意长度**的操作序列后成立。
>
> 实测：depth 7 闭包，|S| = 43，560 个检查点，1.5 s，无反例
> ⇒ **PROVED-UNBOUNDED**。

#### 为什么朴素放大 N 或去掉守卫都不行

无界性的障碍不是"状态多"，而是三个**具体的计数依赖**——它们使"按抽象状态
去重"不再可靠：

| # | 计数依赖 | 后果 |
| --- | --- | --- |
| 1 | 注册表键集在 runtime 最后一个 fiber 消失时才删除（`_teardown` 的 `if not len(fiber.runtime.fibers)`） | 同一投影的两个具体状态（某视图 1 个 vs 2 个 fiber）dispose 后投影不同 |
| 2 | 按"第 i 个 fiber"的结构定向 | 计数不同会选中不同视图，后继不唯一 |
| 3 | dispose 掉同视图多副本之一时该视图仍存续 | 去重后看不到"视图还在"，store 贡献被错误移除 |

#### 解法：存在集投影 + 视图定向 + 幸存二分

- **存在集投影**：抽象状态从"fiber 视图**多重集**"改为"互异视图的**存在集**"
  （去重）——fiber 计数由此彻底离开状态空间。这是无界性的关键一步；
- **视图定向**：操作按"结构序第 i 个**互异视图**"定向，与计数无关（消灭 2）；
- **注册表键集从全局态导出**（= 有存活 fiber 的插件名集合），不再作为独立
  维度（消灭 1）；
- **幸存二分**：每个 dispose 展开**两个**后继——被处置视图消失（计数=1）与
  仍存在（计数≥2），两者都检查性质、都继续展开（覆盖 3 的计数=1 侧）；
  二分后继的全局态按"幸存者继承被处置者的 store 贡献"构造（覆盖 3 的计数≥2
  侧，同时正确处理 1 的键保留语义）。

可达集里二分确实产生新状态（8 个"provider 存活但无 svc@root 条目"的存在集
状态只在开二分后出现）；回归测试 `test_bifurcation_is_not_vacuous` 锁定
"开二分的可达集严格更大"（43 > 36），防止二分退化成空转。

#### 定理的五个前提与机器检查状态

| 前提 | 内容 | 检查方式 |
| --- | --- | --- |
| H1 | 视图完备：视图携带插件主体标签（shape）与全部全局贡献（provides/listens）——同视图 ⇒ 同主体、同贡献 | 投影定义 + 一致性检验 |
| H2/H3 | 计数无关性与逐视图更新一致性：多一份同视图 fiber 不改变任何转移的后继 | **一致性检验**（下） |
| H4 | 幸存者惰性：二分后继 = 继态 ∪ {被处置视图}，幸存者自身不被级联改写 | 一致性检验（公式与实测互证） |
| H5 | 级联完备性：notify 必须触达每一个依赖了被通知服务的 fiber | **INV-10 插桩**（边属性） |

**一致性检验**（H2/H3/H4 的机器检查形式）：对每个可达状态构造"多一份同视图
fiber"的重复实例（代表路径 + 一次对应形态加载），重放全部 13 个操作，要求后继
与期望一致。实测构造 **60 个干净重复实例**、覆盖 **780 个（状态×操作）组合**，
43/43 个可达状态全部通过；期望后继的判定式与 `_bifurcate` 公式直接对比——
公式与实测互为验证。provider 形态被跳过 43 次是合理的：重复 provide 必然失败，
该视图客观上无多副本。

**浸润测试**（无界尺度的经验证据）：3×240 随机步 + 3 组结构化长序列
（50 消费者+提供方逐个逆序卸载、50 效果插件、20 隔离提供方交替加载/卸载），
终态无违规——这是"插件数远超闭包深度"场景的补充证据，不替代定理。

#### 唯一未机器检查的数学步骤

计数 ≥3 与计数 2 在幸存判定上等价。依据是**代码结构事实**：更新函数不读任何
fiber 计数——代码中唯一的计数读取是 `not len(runtime.fibers)`，只测是否归零；
1 vs 2 由一致性检验覆盖，≥3 由该结构事实覆盖。这是整条无界论证中唯一"人论证
而非机器检查"的步骤，在此显式陈述。

#### 无界路线的残余风险

- **字母表边界**：与 §6.5 同（13 元操作未覆盖 accessor/mixin 运行时增删、
  waterfall veto、isolate 嵌套）；
- **交错空间**：与 §6.3 同（收敛后等价，非交错无关性证明）；
- **bail 盲区**：与 §6.4 同（性质集不观测事件派发判据）；
- **计数 ≥3 的结构论证**：见上，未机器检查。

### 6.3 第七轮：把 37 条功能规约全部形式化

`docs/CORRECTNESS.md` §1 的 37 条规约里，第六轮只覆盖了 12 条（经 INV-1~8）。
第七轮把剩余 25 条全部纳入机器检查，并因此新增 **25 条不变量**
（INV-12~INV-36，含 1 条状态性质 INV-17）。逐条映射见
`CORRECTNESS.md` §3.1 的覆盖账；本节记录**做法**与**代价**。

#### 分层字母表：为什么不能一次全上

第七轮结束时操作数达 33 个，若全部进入 BFS：depth 5 已 10279 个存在集状态 /
521 s，且深度每层约 ×5 —— 闭包落在不可行的算力区间。故按"是否改变抽象状态"
把字母表分成三层：

| 层 | 操作数 | 构成 | 验证方式 |
| --- | --- | --- | --- |
| **结构层** `UOPS_CORE` | 23 | 13 种会创建 fiber 的加载 + 生命周期操作 | 存在集 BFS + 幸存二分**闭包**（唯一给出"任意长度"结论的一层） |
| **探针层** `UOPS_PROBE` | 10 | 只读/自限（读服务、读 accessor、`in` 判定、派发诊断、waterfall 探针、根 effect 元数据探针…） | 对**每个**可达状态逐一执行：性质核对 + **投影自环断言** |
| **快档** `UOPS_L5` | 13 | 第六轮的形态集（生命周期主轴） | 回归套件每次改动都跑（depth 7 闭包 / 43 状态 / ~2 s） |

探针层不进 BFS 展开的理由是它们在投影上是**自环**：不创建 fiber、不改全局态，
只把可观测值写进边检查台账。覆盖面由"每个可达状态都执行一遍全部探针"保证，
并附一条**自环断言**作安全阀：若某探针实际改变了抽象状态，它就属于结构层，
必须挪进 `UOPS_CORE` 重跑闭包——否则分层会静默漏掉它的转移。

这个断言当场抓到了一个真实缺陷：`get_scope` 曾让提供方"消失"。根因不是探针
写错了，而是**幸存二分派生的合成状态没有对应的具体路径**（BFS 为它存的是代表
路径，而代表路径的后继是代表后继本身）。修正方式是 BFS 显式记录哪些状态是
二分派生的，探针层跳过并计数——跳过的状态由公式覆盖，不是"没验证"。

#### 投影为 U-6 与 accessor 归属做的两处扩展

- `UFiberView` 加 `depth`（插件祖先数）与 `parent_key`（父视图 key）——
  级联语义的载体。**幸存二分因此改为级联感知**：`_bifurcate`/`_unbifurcate`
  收前态参数，连被处置视图的后代（`_descendants` 传递闭包）一起恢复/移除，
  并同步 store 条目与 props 的 accessor 条目。
- `UFiberView` 加 `accessors`（本 fiber 注册的 accessor / mixin 成员名），
  `UGlobal` 加 `builtin_accessors`（根 fiber 的 16 个内置 mixin accessor）。
  有了逐 fiber 归属，R-6/R-7 的生命周期半条才能成为状态性质 INV-17：
  `props 的 accessor 集 == 根 fiber 内置 ∪ 存活插件视图注册的 accessor 集`。

#### 两处新插桩（进程级、幂等，构造期由 UWorld 收养）

- `ReflectService.accessor`：记录 `(名字, 注册方 fiber)`。记账点在调用
  **成功后**并按身份确认（`props[name] is options`）——同名重复注册会抛错，
  失败者并不持有该 accessor。
- `ReflectService.notify`：记录每条 `internal/service` 事件的
  `(服务名, 作用域 label)`，与观测者的 `alive`/`dead` 标记落在**同一条有序
  日志** `world.event_log` 上。

#### 实测修正了六次建模错误（都由机器检查抓出）

这一轮最值得记录的不是代码，而是**六个我以为对、实际错的建模假设**，
全部由新性质在浅层就撞出来：

1. **E-5 的隔离是"按名字"的**：未隔离的名字沿原型链继承根作用域标签，隔离
   作用域里的监听器本来就该收到它们的根作用域事件。初版按"监听方是否隔离
   加载"二分，把正确行为判成泄漏。
2. **观测器必须与发射方解耦**：观察者若与提供方同插件，它在自己插件的拆卸
   窗口内就被摘除（逆序清 disposer 时监听器先于 provide 的 disposer），
   收不到拆卸期事件——那是 U-3/INV-6 已覆盖的正确行为。改为 `load_iso_pair`：
   同一隔离作用域里加载"提供方 + 独立观察者"两个插件。
3. **期望值必须按发射时刻的存活集计算**：观察者晚于某次事件存在时，不该被
   期望收到那一次。改为按 `event_log` 时间顺序重放并维护存活集。
4. **幸存分支要恢复 accessor 条目**：`_bifurcate` 曾漏掉，导致 INV-17 在
   `SURVIVOR` 分支上误报（存活者仍持有 `acc`，props 却已被摘除）。
5. **accessor 插桩要在调用成功后记账**（见上）。
6. **R-2 是无条件拒绝**：未声明 `inject` 的服务在插件上下文里根本不可达
   （解析链只沿 `fiber.store` 上溯，而 store 只装已声明依赖），与是否已有
   提供方无关。初版写成"有提供方则成功"，被实测纠正。

此外还有两处**模型自身**的缺陷被探针层当场抓出：`waterfall_probe` 每次调用
都往根 fiber 挂一个新监听器（无界增长）；`exporter` 必须注册在**服务**
（`ctx.logger.exporter`）上，`Logger` 实例并没有该方法。

#### 实测数据

| 字母表 | 操作数 | 闭包深度 | 存在集状态 | 检查点 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| `UOPS_L5`（回归快档） | 13 | 7 | 43 | 560 | ~2 s |
| `UOPS_TIER1`（一级结构层） | 18 | 12 | 1416 | 25 489 | 266 s（独占）/ 576 s（并发负载下） |
| `UOPS_CORE`（完整结构层） | 23 | 算力预算内**未闭包**（depth 5） | 10 279 | 62 423 | 545 s（depth 6 未跑完，状态上限 6 万需数小时） |

**结构层（23 元）未闭包这件事必须如实说**：它的深度增长率约 ×5，depth 6 尚未跑完

**13 元与 18 元两个已闭包的字母表**上达成的；23 元字母表目前只拿到"算力预算内
无反例"（depth 5、10 279 个状态、62 423 个检查点），**不等于闭包**。三档强度的
区别见 `CORRECTNESS.md` §3.1。

一致性检验（`UOPS_TIER1`，**全量** 1416 个可达状态 × 5 形态 × 18 操作）：
**0 失败 / 1410 s**——级联感知的 `_bifurcate` 公式与实测在全部（状态 × 操作）
组合上互证成立。探针层在 `UOPS_L5` 的 36 个可达状态 × 10 个探针上全通过
（性质 + 自环断言；另有 7 个二分派生状态无具体路径，由公式覆盖）。

### 6.3 异步交错空间未穷举

每个场景用固定收敛策略（`_settle`，三轮 `await_`）把悬挂任务驱动到收敛后
才投影状态。因此交错维度被"收敛后等价"消解——**不是**证明了交错无关性。

### 6.4 域外缺陷已知存在

§5.1 的 `bail` 判据变异是**真实存在的盲区**：该缺陷若真出现在代码里，当前
性质集不会报警。补齐需要新增性质（事件派发判据），而非扩大搜索。

### 6.5 字母表不完备

`verify.py` 的 `Σ` 有 10 个操作（加载 4 种形态、卸载 3 种选择、更新、重启、
事件派发）；`verify_unbounded.py` 的字母表 13 元（加载 4 种、按互异视图定向的
卸载/更新/重启 8 种、派发 1 种）。两者都未覆盖：`accessor`/`mixin` 的运行时
增删、waterfall 的 veto、`isolate` 的嵌套。这些由 `tests/test_spec.py` 的规约
用例锁定，但**不在**本算法的证明范围内。

## 7. 运行方式

```bash
cd python-cordis

# 无界证明（推荐，主结论）：结构层 23 元字母表 → PROVED-UNBOUNDED
python -W error::RuntimeWarning tools/verify_unbounded.py

# 快速档：只跑证明义务 + 探针层（约 2 s 闭包 + 探针核对）
python -W error::RuntimeWarning tools/verify_unbounded.py \
    --no-mutate --no-soak --uniformity-sample 60

# 完整结构层闭包（小时级算力，发布前跑；一致性检验与变异另计）
python -W error::RuntimeWarning tools/verify_unbounded.py \
    --max-states 400000 --uniformity-sample 0

# 无界证明的单项：--no-mutate 只跑证明义务；--no-uniformity 跳一致性检验；--no-soak 跳浸润
python -W error::RuntimeWarning tools/verify_unbounded.py --no-mutate

# 基数约束路线（交叉验证）：N=2，18.8s 达到闭包 → PROVED
python -W error::RuntimeWarning tools/verify.py --max-depth 16 --plugin-cap 2

# 扩大证明范围：N 每加 1，状态空间与耗时都会增长
python -W error::RuntimeWarning tools/verify.py --max-depth 18 --plugin-cap 3

# 无基数约束（verify.py）：只能给有界结论，裁决为 INCONCLUSIVE
python -W error::RuntimeWarning tools/verify.py --max-depth 5

# 退出码：0 = 无真实反例且域内变异全捕获；1 = 找到反例或域内变异有漏检
# 注意：「闭包未达成」（INCONCLUSIVE）**不**影响退出码——它是稳定的能力
# 边界，不是本次运行的失败。计入的话 CI 会长期红灯，反而使人忽略真正
# 的反例与漏检。
```

两个验证器的结论都锁进了回归测试：`tests/test_closure.py`
（`TestClosureProof` 锁 N=2 闭包；`TestUnboundedProof` 锁无界闭包〔快档 13 元
字母表〕、18 元字母表闭包〔`CORDIS_FORMAL=full` 开启〕、二分非空转、投影有界、
探针层自环、核心字母表预算内无违规、变异全捕获）。

分档模式与 `tests/test_properties.py` 的 `CORDIS_BMC_DEPTH` 同一思路：
默认套件约 6 分钟（跑 13 元快档 + 变异试验台）；`CORDIS_FORMAL=full` 另加
18 元字母表的完整闭包（266 s 独占 / 576 s 并发负载下）。

与测试套件的关系：`tests/` 下的 124 例是**回归防线**（改动后快速确认没有
破坏既有行为），`tools/verify*.py` 是**形式化论证**（给出带明确强度边界的结论）。
两者互补，不可互相替代。
